# Bounded genuine Luxury inquiry runtime

`runLuxuryGenuineInquiryOnce()` adds a callable internal contact/task path using
the existing phase journal, delivery worker and provider adapter. It introduces
no route, startup import, scheduler, store, service or credential configuration.
The original validation profile remains the default. This code does not release
business HOLD or enable unattended commercial processing.

## Contract

- A current accepted release names one to five canonical inquiry IDs and immutable
  fingerprints, the existing Luxury destination and owner, acceptance references,
  and a bounded validity window. References alone do not authenticate approval.
- The source must be a complete authenticated canonical snapshot. Each approved
  record appears exactly once and retains the current thirteen-field event and
  fingerprint contract. Only the supported source routes and allowlisted campaign
  forms are eligible. Internal fixtures are excluded.
- Each event needs a separately authoritative, fresh, event-bound internal-handling
  admission and identity suppression/DND decision. Message text, notes, tags,
  analytics consent and subscriber status cannot approve processing.
- Every source/admission check passes before journal or provider access. Release,
  admission and restored-journal state are checked again before every provider
  mutation. Revocation stops later writes; existing ambiguous intents retain the
  durable worker's conservative uncertainty behavior.
- Genuine tasks and owner notifications have distinct truthful labels. Existing
  validation metadata, manual-baseline handling and default behavior remain intact.
  The recipient is the existing owner mailbox; no customer message, enrollment,
  qualification, financing action or revenue assertion is added.

Dependency objects are trusted server code, never request-body input. This
function is not a public request handler and does not authenticate caller-supplied
dependency implementations.

## Integration and release

Use the same existing source owner and managed journal lifecycle. Wire only
reviewed source, admission and release-revocation readers. The concrete source
adapter is documented separately and currently denies admission because its
authoritative permission/suppression contract is absent.

Actual production recovery and controlled deployed acceptance are separate gates.
Local encrypted-journal fixtures and mocked providers do not establish production
restore, native CRM delivery, inbox receipt or human follow-up. This module does
not alter startup configuration or permit clearing business HOLD.

The existing optional-consent draft extends the payload schema, while current
event identity pins thirteen fields. Its schema and fingerprint applicability
must be versioned/reconciled before selecting that work. Do not silently strip
consent extensions or reinterpret older encrypted-intake/pilot stores as the
current delivery journal.

## Validation

The accompanying tests exercise release/admission holds, injection rejection,
fixture exclusion, whole-batch validation, replay/concurrency, same-email
distinct inquiries, ambiguous writes and positive recovery, restored-journal
holds, genuine labels, the existing owner-only destination and per-write stops.
All inquiries, provider responses and temporary encrypted journals are synthetic.
Repository-wide validation results belong to the draft review receipt; tests do
not constitute a production release.
