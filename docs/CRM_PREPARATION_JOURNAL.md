# Internal CRM preparation journal

`crmPreparationJournal.ts` retains a small encrypted, append-only ledger for internal preparation metadata. It supplements the existing reconciliation planner and canonical sources. It is not a CRM transport, a sent-message log or an acknowledgement checkpoint.

The ledger retains division, non-personal source token, opaque source record ID, source revision, version-bound idempotency key and metadata fingerprint. It reuses the existing metadata validators. Event payloads, names, email addresses, financial details and consent claims are not retained. Callers must derive appropriately scoped opaque identifiers; hexadecimal syntax alone does not prove anonymity or authorization.

Entries are encrypted with AES-256-GCM using a distinct authenticated context and a caller-supplied 256-bit key. New storage directories may be created only as a single leaf beneath an existing canonical private parent. Atomic, synced writes share the existing storage lock and require the exact previous ciphertext revision. Exact replay returns the existing revision without rewriting; conflicting fingerprints, source revision gaps, cross-division source collisions, stale writers, unsafe paths and authentication failures hold. Entries are never trimmed or silently reseeded by a writer with an expected prior revision.

`readCRMPreparationJournal(directory, key)` reports `EMPTY` when a file is absent. That is an observation of this optional ledger, never proof of an empty business pipeline. `retainCRMPreparation(directory, key, expectedRevision, events)` accepts at most 100 events per append and retains at most 1,000 entries. It does not connect to sources or verify the caller's evidence, consent or scope. Old preparation evidence must always be rechecked against current source, mapping and consent state before any future action.

Every snapshot explicitly reports `writesCRM`, `advancesCRMCheckpoint`, `businessDataExecutionAllowed` and `independentRecoveryVerified` as false. Retention is not delivery, and it must never be used to suppress an outstanding CRM write on the assumption that preparation equals successful synchronization.

The journal is an unconnected source component. It has no production initialization, live source adapter, scheduled caller, network transport or automated offsite backup mechanism. The explicit isolated operator command described below uses the already-managed pilot key only for a fixed synthetic fixture. The shared backup module now includes an explicitly separate preparation profile: `exportCRMPreparationBackup` and `restoreCRMPreparationBackup`. It authenticates the retained entry count and sequence against decrypted contents, refuses overwrite, and requires pre-existing private canonical directories. This profile does not extend the old independent pipeline/intake verifier or recovery receipt. Before activation, establish reviewed source scope, key recovery, backup export/restore coverage and independently retained recurring copies. Windows deployments additionally require verified private ACLs; this module's POSIX permission checks do not establish Windows ACL safety.

Validation: `node --test tests/crmPreparationJournal.test.mjs` covers encrypted persistence, replay, conflict, concurrent writers, authentication/tampering, private paths, actual file symlink/hardlink rejection, unsafe-ancestor side-effect prevention, lost-state holds and a fresh-process recovery from an independent ciphertext copy. Test keys are ephemeral and passed to the child through stdin, not command arguments or environment. These synthetic tests do not establish operational offsite recovery.

The operator-only `scripts/crm-preparation-backup.mjs export|restore ARCHIVE DIRECTORY` accepts the 64-character lowercase hexadecimal key through stdin (optional final LF), never arguments or environment. Keep the key in an approved secret manager and pass it through an anonymous pipe. It does not create directories for you or attest independent retention.

`node scripts/pilot-crm-preparation.mjs initialize` is an explicit isolated-pilot-only fixed-fixture command. It checks service identity, synthetic-only mode, mount, managed key and disabled connectors before initializing one separate opaque preparation fixture and verifying its encrypted local backup. `verify` checks subsequent reads and recoveries without initializing. Existing retained history prevents reseeding after primary loss. This command is not scheduled and adds no operational agent or customer source. Its independent recovery must be separately verified on an approved endpoint before claiming that evidence.

The standalone `crm-preparation-independent-recovery.mjs restore|verify ARCHIVE TARGET` independently authenticates only that fixed preparation fixture, rejects wrong keys and altered ciphertext, and refuses to overwrite an existing restore directory. It has no application imports and can run on an approved independent endpoint. The key arrives only through stdin; verify current-user ACLs separately on Windows. Its output cannot attest recurring transport or business readiness, and cannot refresh the existing pipeline/intake receipt for this third format.
